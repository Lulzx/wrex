SECTION 1
OVERVIEW
1.1

INTRODUCTION.

Wrex compiles each fold, scan and treefold into a parallel plan or a sequential loop. A loop composes step functions, and composition is associative. When those functions stay inside one family closed under cheap composition (a representation), the loop runs as a parallel scan with the sequential answer, bit for bit, first trap included (figure 1-1).

1.2

FUNCTIONAL DESCRIPTION.

The type checker hands each loop site to representation inference, which normalizes the step body into ring or lattice normal form and matches it against families F0 through F6 (section 2). A site with no match runs sequentially, and “wrex explain” names the smallest subterm responsible. A certified site goes to plan selection, which evaluates the cost model on the actual input size n (section 3, figure 1-2).

1.2.1

Law L3 Check.

Families prove associativity and identity once; only L3, ev(ρ(x), s) = step(s, x), depends on the program. Both sides reduce to canonical normal forms, so an inference error costs speed, never correctness.

1.2.2

Rejection Report.

For the logistic step r·s·(100 − s), “wrex explain” prints “The new value contains `s * s`, which has degree 2 in the state” and the loop runs sequentially.

SECTION 2
REPRESENTATION FAMILIES
2.1

INTRODUCTION.

A representation is a tuple (R, , ι, ρ, ev). R holds summaries of step functions, ρ maps an input to one, composes two (first left, then right) and ev applies one to a state. Wrex ships seven fixed families. Their associativity and identity laws hold once for the family; only L3 depends on the program (figure 2-1).

2.2

FUNCTIONAL DESCRIPTION.

F1 is preferred over F2 when both apply, because its compose is cheaper. F5 splits the state into a finite control part, which depends only on itself and the input, and a payload whose update lies in a family for each fixed control state. A word counter looks inherently sequential, yet its control has two states and its counter is affine in each (figure 2-2, detail A).

2.2.1

Clamp Composition.

Two clamps make one: (a₁, l₁, h₁) (a₂, l₂, h₂) = (a₁ + a₂, min(max(l₁ + a₂, l₂), h₂), max(min(h₁ + a₂, h₂), l₂)), so saturating counters and running maxima scan at six operations per merge.

2.2.2

Floating Point.

No family admits f64 state, because floating-point addition is not associative. An f64 fold runs sequentially unless its function carries @reassoc (section 3).

SECTION 3
EXECUTION PLANS AND COST MODEL
3.1

INTRODUCTION.

A certificate makes a parallel plan possible; the cost model decides whether to run it. The guard at each call site evaluates the plan formulas on the actual input size n, so one loop can run sequentially on short inputs and in parallel on long ones. Every plan returns the same answer, so selection affects only speed (figure 3-1).

3.2

FUNCTIONAL DESCRIPTION.

Phase 1 splits n inputs into p contiguous blocks, and each worker composes ρ(x) across its block. Phase 2 forms the exclusive prefix of the p summaries and evaluates each block’s start state from s₀. Phase 3 replays the original step from that state, so a scan writes exact outputs. A fold skips phase 3 and combines the summaries by a balanced tree (figure 3-2).

3.2.1

Trap Precision.

A summary carries the index of its first trap, and keeps the smaller index when both operands trap. The parallel plan therefore reports the trap the sequential program would, at the same position.

3.2.2

Plan Refusal.

A family whose compose costs more than 4096 operations never gets a parallel plan, however large n is. Its per-element ρ cost grows with the same size, so a large enough table is a sequential loop with extra steps.

SECTION 4
TREE FOLDS AND BACKENDS
4.1

INTRODUCTION.

A treefold gives one arm per constructor, and recursive fields stand for the folded results of the children. When every one-hole context of every arm lies in a family, the runtime contracts the tree in rounds of logarithmic depth whatever its shape. A list-shaped tree, which gives fork-join nothing to split, still runs in parallel (figure 4-1).

4.2

FUNCTIONAL DESCRIPTION.

Three backends run certified loops. The interpreter executes every plan and is the reference. The C backend emits standalone C with pthreads for folds and scans in all families F0 through F6; it reads parameters, n, inputs and the initial state on stdin and takes the thread count as its first argument. The GPU backend lowers folds and scans to tinygrad tensor operations and falls back to the exact CPU plan on any failure (figure 4-2).

4.2.1

Nested Folds.

The outer plan owns the parallelism. A fold inside a step that the outer plan is already evaluating runs sequentially.

4.2.2

Tree Plan Choice.

Every tree node records its size and height when built. The guard compares ForkJoin, (n/p)·c_arm + h·c_sync, with Contract and takes the cheaper; a balanced tree needs no contexts.
