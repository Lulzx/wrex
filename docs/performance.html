Performance

This page tries to answer a fairly narrow question: if you write a program once in Wrex, how fast does it run under each of the ways Wrex knows how to execute it? There are three of them: the reference interpreter running the program step by step, the same interpreter running the parallel plan, and the C code that wrex codegen produces. To keep those numbers honest, each chart also shows the same loop written the obvious way, sequentially and by hand, in C, Rust, Go, Java and Python. Further down, I also go through what it would take to get the parallel version by hand in those languages.

One rule applies to every number here. A plan’s timing only counts if its output is identical to the reference, down to the bits and down to which trap fires first. wrex bench checks this before printing anything. A fast plan that gives a different answer is a bug, so it doesn’t get a time.

What this would take in other languages

In Wrex, each of these benchmarks is a single sequential fold, scan or treefold. Representation inference then works out the composition law and checks that it holds. In most other languages the sequential loop is just as short, so the interesting question is what the parallel version costs. The short answer is that it’s usually a second program, which someone has to write and verify by hand. Here is what that looks like case by case.

Prefix sum

In Wrex: one scan (F0)

This is the easy case. In C, Rust or Go, the sequential version is a plain loop. For the parallel version you can either write the blocked scan yourself (summarize each block, scan the summaries, then replay) or use C++’s std::inclusive_scan with a parallel execution policy. In Python, numpy.cumsum is fast, but it only works for built-in operations like +.

Linear recurrence

In Wrex: one scan (F1)

Here things get harder. The step b * rate + deposit isn’t a binary operation on balances, so library scans don’t directly apply. The trick is to notice that each step is an affine map (a, b), scan over those pairs with a composition rule you derive yourself, and then apply the result. That derivation is exactly what F1 is, and in C, Rust, Haskell or anything else you would be doing it by hand.

Saturating counters

In Wrex: one scan with clamp (F3)

Every mainstream language writes this as a sequential loop. There’s a tempting NumPy shortcut (cumsum, then clip), but it gives the wrong answer: once you’ve hit the cap, a negative delta has to count down from the cap, and the shortcut counts down from the unclipped total instead. A correct parallel version needs the shifted-clamp composition law, and I’m not aware of any standard library that provides it.

Tokenizer / word count

In Wrex: one state-machine fold (F5)

The sequential version is a state machine, whether you write it in C, Rust, Go, Java or Python. To parallelize it, you represent each character as a transition function over states, compose those tables, and carry the counter separately for each state. This is the approach from Mytkowicz et al., Data-Parallel Finite-State Machines (ASPLOS 2014), and in practice people re-implement it from scratch each time, because regex and text libraries don’t expose anything like it.

Viterbi (max-plus)

In Wrex: one fold (tropical F2)

Sequentially, this is a dynamic-programming loop. In parallel, you compose 2 by 2 max-plus matrices, one per step. BLAS and NumPy don’t support the tropical semiring, so you end up writing the matrix multiply by hand as well.

Expression trees

In Wrex: one treefold, contexts inferred

Fork-join recursion (rayon’s join in Rust, par in Haskell, goroutines in Go, ForkJoin in Java) works well as long as the tree is balanced. If the tree is shaped like a list, every one of these degenerates into a sequential walk down the spine. The fix is tree contraction (Miller and Reif) with contexts that you derive yourself, and here too, no standard library does it for you.

It’s worth being fair to the data-parallel languages here. Futhark, Halide and Accelerate all have a parallel scan primitive. The difference is in who is responsible for correctness: you hand them an operator and promise that it’s associative, and the compiler trusts you. Wrex goes the other way. It starts from the sequential step, infers the operator, and checks the law before parallelizing anything. If no law applies, it runs the code sequentially and tells you which subterm was responsible. You can also supply your own operators (family declarations, spec 6.8), and the compiler machine-checks those where they are declared.

Where the speed comes from, and where it doesn’t

The interpreter numbers are unflattering, the generated C ones less so, and both have a reason worth going through.

  • The reference interpreter is a tree-walking interpreter written in Python. Its job is to define the semantics that every other plan has to match, and it pays for that with speed. At n = 50,000 it is 62 to 280 times slower than the same loop written in plain Python, and plain Python is in turn 20 to 190 times slower than the compiled languages.
  • A parallel plan changes the shape of the work, but it doesn’t make the interpreter itself any faster. A parallel scan has to summarize blocks and then replay them, and in Python each of those steps pays interpreter overhead. This is why Par loses to Seq on every row. It’s also why, under --plan=auto, the cost model keeps these scans sequential.
  • wrex codegen is where the composition law turns into speed, and interestingly, most of that speed doesn’t come from threads. A plain sequential loop is limited by its dependency chain: each step has to wait for the previous one. Because the generated code knows how to compose steps, it splits the input into several sub-blocks and advances them side by side on one core, so the processor works on independent chains at once. That alone makes the linear recurrence about twice as fast as the hand-written C loop, and it puts saturating counters and Viterbi ahead too. Prefix sum and the tokenizer have steps so cheap that there is no chain to break. There the generated C runs the plain loop: it ties on the prefix sum and finishes the tokenizer 2 µs behind C, which reads its text as bytes in a loop the compiler vectorizes.
  • Threads only enter at larger sizes. Creating and joining a thread costs about 15 µs on this machine, which is more than any of these loops takes at n = 50,000, so the generated code stays on one core until each worker has at least 131,072 elements. At 10,000,000 elements, with 8 workers, it is 1.4 to 5.7 times faster than the hand-written C loop on all five benchmarks.
  • The tokenizer is a state machine, in the sense that whether you’re currently inside a word determines what the next character does. Even so, it has an F5 representation, so it scans the same way the prefix sum does. The list-shaped tree is interesting for the opposite reason: it has no balanced parallelism at all, but it still contracts in a logarithmic number of rounds. At 3,000 nodes in Python, though, constant factors swamp that advantage, as the chart shows.
  • There are also things Wrex deliberately won’t do for speed. It doesn’t reassociate floating point unless you opt in with @reassoc and accept a stated error bound. It doesn’t approximate a step it can’t represent. And it doesn’t report a later trap just because an earlier one happened to sit in a different block. For example, the fold in examples/logistic.wrx has no representation, so it runs sequentially, and wrex explain tells you why.

Test setup

Everything was measured on an Apple M4 Pro (12 cores) with 24 GB of RAM. The loop benchmarks are the Appendix B programs in benchmarks/, run on n = 50,000 seeded random inputs, and the hand-written versions in benchmarks/native/ read exactly the same inputs. The interpreter times use Python 3.15.2 and are the fastest of 3 calls. The hand-written loops were built with Apple clang 21 (-O2), rustc 1.99.1 (-O), Go 1.27.3 and OpenJDK 27.0.1, and each was timed in its own process as the fastest of 200 runs (20 for Python), which also gives the JVM time to compile the loop. The generated C was compiled with -O2 and timed through its WREX_BENCH hook, which runs the computation 200 times in one process and reports the fastest, the same as the hand-written loops. Every result was checked against the reference interpreter before any time was reported. On other hardware the absolute numbers will differ, but the agreement between implementations should not.

Run it yourself

python3 -m venv .venv && .venv/bin/pip install -e .
.venv/bin/wrex bench --n=50000        # interpreter plans, agreement-checked
.venv/bin/python benchmarks/native/run.py   # every chart on this page, checked
.venv/bin/wrex codegen benchmarks/prefix_sum.wrx --fn=prefix_sum -o ps.c
cc -O2 -o ps ps.c                     # standalone, reads n, inputs, state on stdin

The Wrex programs live in benchmarks/ and the hand-written versions in benchmarks/native/. run.py needs cc, rustc, go and a JDK on your PATH, and writes its numbers to benchmarks/native/results.json.
