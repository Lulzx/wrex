Performance

Even though most benchmarks aren’t worth the pixels they’re printed on, people seem to like them, so here are a few. Ours come with one twist: every plan shown here is required to produce the identical result, bit for bit, including which trap fires first — and the harness checks that before it reports any time. A faster plan that answers differently is not a faster plan; it is a different program.

Why is Wren fast? Why is Wrex… like this?

Wren’s page sorts languages into four buckets, from tree-walk interpreters up to statically typed compiled languages, and places Wren in the second bucket — bytecode — arguing that is the sweet spot for a simple implementation. Wrex spans the buckets deliberately, and the chart above is what that looks like when you measure it:

  • The reference interpreter is a tree-walk interpreter — bucket one, the slow one. It exists to define the semantics, not to win benchmarks. Seq is its time, and it is the baseline everything else must match exactly.
  • Parallel plans change the shape of the work, not the speed of the interpreter. A parallel scan first summarizes blocks, then replays them; in Python each of those steps costs interpreter overhead, so Par loses to Seq at n = 50,000 on every row. Wrex’s cost model knows this and, under --plan=auto, keeps these scans sequential. Publishing a “parallel” bar that loses is the honest version of this chart.
  • The generated C is the compiled bucket. wrex codegen emits the same summaries/⋄/ev as standalone C with pthreads — all three scan phases run in parallel there — which is where the 13–110× comes from. Its time here even includes process startup and parsing 50,000 integers from stdin; at this size that I/O, not arithmetic, is most of the 4–8 ms, which is also why 1 vs 8 workers barely differ on these rows. The interpreter numbers, by contrast, time only the call itself.
  • Some shapes parallelize that do not look parallel. The tokenizer is a state machine — whether you are inside a word decides what the next character does — yet it carries an F5 representation, so it scans like the prefix sum. The list-shaped tree has no balanced parallelism at all, and still contracts in logarithmic rounds; at 3,000 nodes in Python, constant factors hide that, which the chart also shows.
  • What Wrex will not do for speed: reassociate floating point (unless you opt in with @reassoc, accepting a stated error bound), approximate an unrepresentable step, or report the second trap because the first was in another block. The logistic-map fold in examples/logistic.wrx has no representation; it runs sequentially at whatever speed that is, and wrex explain tells you why.
How these were measured. Apple M4 Pro (12 cores), 24 GB RAM, Python 3.15.2, Apple clang 21, 8 workers. Loop benchmarks use the Appendix B programs in benchmarks/ with n = 50,000 seeded-random inputs; interpreter times are the best of repeated calls with the data already in memory, and every plan’s result is compared for exact agreement before timing is reported. The C binaries are generated from the same programs, compiled -O2, warmed once, then timed best-of-5 as whole processes reading their input from stdin. Your numbers will differ; the ordering — and the agreement check — should not.

Reproduce it

python3 -m venv .venv && .venv/bin/pip install -e .
.venv/bin/wrex bench --n=50000        # interpreter plans, agreement-checked
.venv/bin/wrex bench --n=200 --c      # plus generated-C timings
.venv/bin/wrex codegen benchmarks/prefix_sum.wrx --fn=prefix_sum -o ps.c
cc -O2 -o ps ps.c                     # standalone; reads n, inputs, state on stdin

The benchmark programs are in benchmarks/; the harness is wrex bench (wrex/bench.py). Like the page that inspired this one: shorter bars are better, and benchmarks still aren’t worth much more than the pixels they’re printed on — unless they also prove the answers agree.
